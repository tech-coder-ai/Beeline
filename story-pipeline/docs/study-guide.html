How the Story-to-YouTube pipeline was designed and built

This guide follows the reasoning behind each part of the app: what was built, in what order, which alternatives were rejected, and which bugs testing caught. Read it next to the code and you should be able to build a similar pipeline yourself.

How to use this guide

The app lives in story-pipeline/ on branch claude/zealous-babbage-efuf30 of your Beeline repository. It implements the "Story-to-YouTube" plan from your ChatGPT conversation as a working MVP. It covers discovery, the rights gate, adaptation, character sheets, scene art, voices, rendering, QC and publishing, plus an Angular dashboard.

Every section names the file that implements what it describes. The best way to learn from it is to run the app first, then read the guide with the code open:

cd story-pipeline/backend
python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"
.venv/bin/pytest                          # 26 tests, including full offline renders
.venv/bin/uvicorn app.main:app --port 8000
cd ../frontend && npm ci && npx ng serve   # dashboard on http://localhost:4200

In the dashboard, open Story library → Discover stories, run the library connector, approve a fable, create a project and press Run. You will hit three approval checkpoints and end with an MP4, subtitles, a thumbnail and a QC report.

No GPU or API keys needed to startOut of the box the app uses offline stand-ins: a rule-based scene splitter instead of an LLM, Pillow-drawn storyboard cards instead of a diffusion model, FFmpeg's built-in flite voice, and a "dry run" publisher. Section 9 shows how to switch each one to the real thing by changing configuration only.

The one big decision: a pipeline, not an agent

The most important sentence in the original plan was: "don't build one giant AI agent that does everything. Build a sequence of independent, testable services." Almost every other choice follows from it.

An agent that "makes a video from a story" fails in ways you can't see, can't resume, and can't test. A pipeline of stages gives you:

  • Inspectable intermediate results. The story bible, the scene list, each image, each audio clip and the timeline are all saved. When the video is wrong, you can see which stage went wrong.
  • Cheap retries. If image 18 of 30 fails, only image 18 is redone.
  • Human control at the right moments. You approve the script before paying for art, and the art before paying for rendering.
  • Swappable parts. Replacing the image model doesn't touch translation or publishing.

The working rule: use AI for the creative work and ordinary code for everything that has a right answer. In this codebase, an LLM writes the story bible, the script, translations and video titles. Plain code handles validation, timing, file management, retries, rights checks, QC and uploading.

What was left out on purpose

No LangChain, Celery, Kafka, Redis or Kubernetes. Each one solves a problem this system doesn't have yet. A single workstation runs one GPU job at a time. Prompting is two well-defined calls, and those don't need a framework. The extension points are in place (a provider protocol, a jobs table, a database_url setting) so you can add these tools when real throughput requires them. Adding infrastructure before you need it is the most common way projects like this stall.

The build order, and why it went in that order

The order matters more than people expect. Each step gives the next one something solid to stand on, and the riskiest pieces (orchestration and resumability) were built before any stage depended on them.

  1. Configuration files. config/pipeline.yaml, languages.yaml, prompts/*.md. Writing these first forces you to name every choice (provider, model, limits, checkpoints) before writing code that assumes one. Prompts live here too, so you can tune them without a deploy.
  2. Typed settings loader. app/config.py. Pydantic models for every YAML key, SPA_* environment overrides, and a config_version hash stored on every project and job. A typo like provider: olama fails at startup, not two hours into a render.
  3. The state machine. app/domain/states.py. One table of stages: what each requires, what it produces, and which checkpoint it raises. The API, the engine and the UI all read this table, so they can't disagree about what comes next.
  4. Database models. app/persistence/models.py. The twelve entities from the plan's data model, plus a fingerprint column on everything that gets generated (more on that in D6).
  5. Provider interfaces with two adapters each. A real adapter (Ollama, ComfyUI, Piper, YouTube) and an offline one, written together. The offline adapters made it possible to test every later step on a laptop.
  6. The workflow engine and runner. app/workflow/. Queueing, the retry policy, checkpoints and crash recovery, built before any real stage existed. Engine tests use fake stage handlers that fail on purpose.
  7. The stages, in pipeline order. Discovery and rights, then script, characters, scenes, audio, render, QC and publish. Each stage was run for real before starting the next, because each consumes the previous stage's output.
  8. The API. Thin routers over the engine and services. Business rules such as "no project from an unapproved source" are enforced here and in the engine, never only in the UI.
  9. Tests, then a live 1080p run. The test suite renders tiny 320×180 videos to stay fast. A full-resolution run through the HTTP API then caught problems tests can't see, such as subtitle size.
  10. The dashboard last. When the UI comes last it can't hide missing backend rules, and every screen is a view of state that already exists.

Decision records

Each record follows the same shape: the situation, the choice, what else was considered, and what the choice costs. This format (an "architecture decision record") is worth copying into your own projects.

D1Configuration first, typed, versioned

Context
The plan has many interchangeable parts: LLM, image engine, voices, languages, checkpoints, video size. These will change far more often than the code does.
Decision
YAML files validated by Pydantic (config.py), environment-variable overrides for the common switches, and a 12-character hash of both YAML files stored as config_version on each project and job.
Alternatives
Constants in code (every change needs a deploy). Untyped dicts (typos surface at runtime).
Consequence
You can always answer "which settings produced this video?" The Settings screen calls /api/health, which checks the configured models, voices and workflows against what is actually installed.

D2An explicit state machine in one table

Context
The plan lists the states CREATED → SOURCE_APPROVED → SCRIPT_READY → … → UPLOADED. Three parts of the system need to know what may run next.
Decision
A StageSpec list (domain/states.py) with requires, produces and checkpoint fields. A stage may re-run once its prerequisite is reached, but can never skip ahead.
Deviation
One state was added that the plan didn't have: QC_PASSED. The plan jumped from RENDERED to QC_APPROVED, which merged "the machine checks passed" with "a person approved it". Those are separate facts, and the publish gate needs to tell them apart.
stateDiagram-v2
  [*] --> SOURCE_APPROVED: project created (rights approved)
  SOURCE_APPROVED --> SCRIPT_READY: script
  SCRIPT_READY --> CHARACTERS_READY: characters (after approval)
  CHARACTERS_READY --> SCENES_READY: scenes (after approval)
  SCENES_READY --> MOTION_READY: animate (no-op for illustrated)
  MOTION_READY --> AUDIO_READY: audio
  AUDIO_READY --> RENDERED: render
  RENDERED --> QC_PASSED: qc
  QC_PASSED --> QC_APPROVED: human approves final cut
  QC_APPROVED --> UPLOADED: publish

D3The database is the job queue

Context
Stages take seconds to minutes, and the process may restart mid-render.
Decision
A workflow_jobs table plus one worker thread that polls for QUEUED or due RETRY_PENDING rows (workflow/runner.py). On startup, rows stuck in RUNNING are put back in the queue. Only one job runs at a time; parallelism happens inside a stage, such as max_parallel_scenes.
Alternatives
Celery with RabbitMQ or Redis: more moving parts, and it still needs a database for history. asyncio background tasks: lost on restart.
Consequence
The queue survives crashes for free, and job history is the same rows the UI shows. One job at a time is deliberate: on a single GPU, two heavy stages together usually run out of memory.

D4One provider interface per capability

Context
The plan says "do not let application code call Ollama directly", and that image, speech and video generation "should not be forced into a single LLM interface".
Decision
Four separate Protocols (LLMProvider, ImageProvider, TTSProvider, Publisher). providers/registry.py is the only file that knows concrete classes. Errors share one rule: ProviderError(transient=True) means "worth retrying" and ProviderUnavailable means "use a fallback".
Consequence
Switching ComfyUI for another engine means writing one class with one method. The offline adapters keep the full pipeline runnable in CI.
class LLMProvider(Protocol):
    name: str
    async def generate_text(self, prompt: str, system_prompt: str | None = None) -> str: ...
    async def generate_json(self, prompt: str, schema: dict, system_prompt: str | None = None) -> dict: ...
    async def health(self) -> dict: ...

D5Structured LLM output, in three layers

Context
Later stages must never have to "interpret" free text. The renderer can't ask the model what order the scenes go in.
Decision
  1. Constrained decoding. The Pydantic schema is sent as JSON Schema (format in Ollama, response_format on OpenAI-compatible servers), so the output is well-formed JSON.
  2. Validation and repair. generate_model() validates with Pydantic and, if that fails, re-prompts with the exact validation errors, up to json_repair_attempts times.
  3. Domain checks. story/checks.py catches what a schema can't: unknown speakers, duplicate or out-of-order scenes, a missing protagonist, an abrupt ending, too much text for the duration, or copying too close to the source. Errors go back to the model as a "fix these problems" note for one more draft.
Fallback
With no LLM, a rule-based adapter (story/heuristic.py) splits the source into scenes, detects characters and attributes quoted speech to the nearest named character. Because it reuses the source text word for word, it is allowed only when the license permits verbatim use. Otherwise the stage fails with a clear message.

D6Fingerprints make every stage resumable

Context
The plan's critical requirement: "if generating scene 18 of 30 fails, rerunning the job must not regenerate scenes 1–17."
Decision
Every generated item stores a hash of all the inputs that affect it. Before generating, a stage computes the hash. If it matches the stored one and the file is still intact, the item is reused.
Consequence
This single idea handles retries, crash recovery, targeted regeneration ("new seed" changes the hash) and dependency tracking. A scene's hash includes its characters' reference-sheet checksums, so redrawing a character automatically redraws every scene that character appears in, and no other scene.
# services/scenes/service.py
fp = fingerprint("scene", image.name, image.model, prompt, negative_prompt,
                 sc.seed, w, h, ref_sums)          # ref_sums = checksums of character sheets
if sc.fingerprint == fp and ctx.assets.is_valid(db, sc.image_asset_id):
    reused += 1                                     # nothing that matters changed
    continue

This shows up in practice. The first render of the Town Mouse video took 113 s. After the subtitle fix (see section 7), the re-render took 38 s. Images and timing hadn't changed, so all six scene clips were reused and only the final encode ran again.

D7A single asset registry, with atomic writes

Decision
Business tables never store file paths. They reference an Asset row that owns the path, SHA-256 checksum, size, provider, model, prompt and seed (services/assets.py). Files are written to name.part and then renamed. Paths are checked so they can't escape the project folder.
Consequence
You can reproduce any image from its row. A crash never leaves a half-written file under the real name. "Is this asset valid?" is one check: the row exists, the file exists, and the size matches.

D8The rights gate is code, and a person decides

Context
Being publicly accessible doesn't mean you may adapt something. "Never infer approved because a local LLM says the story is old."
Decision
Connectors only suggest a license. Discovery sets review_required (a license claim exists) or pending (no claim). Approval needs a license type, evidence (a URL or notes), and allowed uses that include adaptation. Attribution text is required if the license demands it (services/rights/service.py). The gate is checked when a project is created, again in QC, and again right before upload, because rights can be revoked.
Extra check
When a license doesn't permit verbatim use, a check measures how many of the script's 8-word sequences appear word for word in the source. Above 60% (configurable), the script is rejected as too close to the original.

D9Scenes store spoken lines in order (a correction during the build)

Context
The plan's scene schema had separate narration and dialogue fields.
Problem
With separate fields, you lose when each line is spoken. "The Mouse pleaded: '…spare my life…' The Lion laughed and let him go" can't be voiced correctly from two lists.
Decision
Changed to an ordered lines: [{speaker, text}] list, where speaker is "narrator" or a character id. Audio, subtitles and timing all follow this order.
Lesson
Check a schema against the stage that consumes it, not only the one that produces it. The problem only showed up when writing the audio stage.

D10Timing comes from measured audio

Decision
One WAV per spoken line per language. The timeline (rendering/timeline.py) sizes each scene from the measured length of its audio: padding + each line + gaps + padding, never shorter than min_scene_seconds, rounded to whole frames so audio and video never drift. The script's duration_seconds is only an estimate.
Consequence
A Hindi line that runs longer than the English one simply makes that scene longer in the Hindi video. You can fix one mistranslated line and re-voice it alone. Subtitles come from the same timeline, so they always match the audio.

D11The application plans the video and FFmpeg renders it

Decision
Three FFmpeg steps (rendering/ffmpeg_render.py):
  1. One clip per scene: the image is upscaled 2× (to avoid zoom jitter), given a Ken Burns move with zoompan, and short fades. Clips are cached by fingerprint and shared across languages.
  2. One narration track: each line is placed at its exact start time with adelay and mixed with amix. Long filter graphs go in a script file instead of the command line.
  3. Final mux: concatenate the clips, normalise loudness with loudnorm (−16 LUFS), burn in the subtitles, and include them as a soft subtitle track. Optional background music is lowered under the voice with sidechaincompress.
Alternatives
MoviePy or a Python video library: slower, and still FFmpeg underneath. One giant filter graph: no per-scene caching.

D12QC measures the actual output files

Decision
Twenty checks, each pass, warn or fail, run on the real MP4 with ffprobe and FFmpeg's analysis filters (quality/qc.py):
  • Format: resolution, frame rate, codec, duration against the timeline.
  • Audio: audible narration (mean volume), clipping (peak), long silences.
  • Black frames.
  • Subtitles: count, overlaps, timing range, reading speed.
  • Thumbnail: size and the 2 MB limit.
  • Metadata: lengths, YouTube's ban on <>, attribution, AI disclosure.
  • Rights, and whether any line used a fallback voice.
Split of work
Anything measurable is checked by code. "Is this story good?" is the job of the human final-cut approval.

D13Checkpoints, and why approving does not upload

Decision
Approval mode pauses after the script, after the character sheets, and after QC. Approving continues the pipeline. Rejecting sends the project back to the start of that stage, and for visual checkpoints gives new seeds so the next run draws something different. publishing.require_approval forces the final human check even in fully automated mode.
Correction
The first version continued straight from "approve final cut" into uploading. The test suite caught it, and it was changed: in approval mode, publishing is a separate, deliberate action where you choose visibility. Approving content and publishing it are two separate decisions.

D14Publishing is idempotent

Context
"A network timeout does not prove that YouTube rejected the upload." A naive retry can post the same video twice.
Decision
Each language gets one Publication row with a stable attempt_id, also added to the video's tags as spa-…. The row is marked uploading and saved before the API call. Every attempt after the first calls find_existing(attempt_id) before uploading again (services/publishing/service.py).
sequenceDiagram
  participant E as Publish stage
  participant DB as Database
  participant YT as YouTube
  E->>DB: Publication(attempt_id) status=uploading (committed)
  E->>YT: videos.insert (tag spa-attempt)
  YT--xE: timeout (but the video was created)
  E->>DB: status=failed, retries=1 -> job RETRY_PENDING
  Note over E: next attempt
  E->>YT: find_existing(attempt_id)?
  YT-->>E: found video_id
  E->>DB: status=uploaded (no second upload)

The test test_publish_timeout_is_reconciled_not_duplicated simulates exactly this and checks that the publisher's upload method was called once.

D15The UI is thin and the backend has the final say

Decision
Angular components hold only view state, in signals. Every rule lives in the API: one active job per project, checkpoint gates, the rights gate and the publish gate. The project page polls every 1.5 s while a job runs and every 8 s otherwise. core/models.ts mirrors api/serializers.py, so the contract lives in one place on each side.
Consequence
A buggy or hand-crafted request can't publish an unapproved video, because the server refuses it with HTTP 409.

Adding AI animation (a change after the first build)

The first version produced "illustrated narration": still images with camera moves, which was the plan's recommended MVP. After it worked, you asked which local model generates the video and said you have 48 GB of GPU memory. That justified the plan's option B, hybrid animation: real AI motion clips for a few key scenes, stills with camera moves for the rest. It's also a good example of extending a pipeline without breaking it.

D16Hybrid animation as its own stage, after the stills are approved

Model choice
Wan 2.2 14B image-to-video, run in ComfyUI with fp8 weights. In the 2026 comparisons I checked, it was the consensus pick for image-to-video motion quality, and it's Apache 2.0, which matters for a monetised channel. LTX-2 is faster and adds audio, but needs a commercial licence once revenue passes $10M. The fp8 14B model needs about 20 GB of VRAM, so 48 GB runs 1280×720 with room to spare.
Decision
A new stage animate between scenes and audio, with a new status MOTION_READY (services/animation/service.py). It only acts for projects whose style is hybrid_animation. For illustrated projects it finishes instantly with "skipped".
Why a stage
Image-to-video costs minutes of GPU per clip, far more than any other step. As a separate stage it:
  • runs only on stills a person has already approved
  • has its own retry budget and fingerprint cache
  • shows its own timing on the Overview, where it will almost certainly become the bottleneck
Which scenes
The script prompt asks the LLM to set animate: true and write a short motion_prompt for at most N scenes: the hook, action and the emotional peak. Code then enforces the cap (max_animated_scenes, default 3). If nothing is marked, the opening scene is animated. The LLM makes the creative choice; code enforces the budget.
Rendering
An animated scene plays its clip, about 5 s (81 frames at Wan's native 16 fps), scaled to the output size. If the narration runs longer, the last frame is held with tpad=stop_mode=clone. The motion clip's checksum is part of the clip fingerprint, so a new motion clip re-renders just that scene.
GPU sharing
One job runs at a time (D3), and the stage calls ComfyUI's /free when it finishes. The Ollama adapter now sends keep_alive; set it to "0" so the LLM releases VRAM between calls.
Honesty
The bundled comfyui-workflows/image_to_video_wan22_14b.json was written from ComfyUI's native Wan nodes and has not been run. The recommended path: get ComfyUI's own Wan 2.2 template rendering, export it in API format, and put the {{image}}, {{prompt}}, {{seed}}, {{frames}}, {{fps}} tokens into it. The token system exists so you're never locked into a hand-written graph.

What changed, file by file

This is the pattern for adding any new capability to the pipeline:

  1. Config: a new models.video block (config.py, pipeline.yaml).
  2. State machine: one StageSpec row and one status (domain/states.py). The API and UI picked up the new stage automatically because they read this table.
  3. Schema: animate and motion_prompt on SceneSpec, and four motion_* columns on Scene.
  4. Provider: a fifth interface, VideoProvider, with ComfyUI, placeholder and none adapters. The ComfyUI HTTP code moved into a shared providers/comfy_client.py used by both images and video.
  5. Service: the stage itself, with fingerprints, partial failure, cancellation, and freeing VRAM.
  6. Renderer: a motion_path on TimelineScene and a render_motion_clip branch.
  7. Tests: scene selection, last-frame hold, a hybrid end-to-end run with clips reused on re-run, and the illustrated skip.
  8. UI: a style picker, motion clips in the Scenes tab, and a health card.
Lesson: you need migrations once there is real dataAdding the motion_* columns works on a fresh database, but create_all never alters an existing table. An existing data/pipeline.db has to be deleted or altered by hand. This is the moment the Alembic exercise below stops being optional.

Bugs found while building

These were real, and each one teaches something general.

1. A new row's defaults are empty until it is savedPublication(...) had retries=None and id=None right after creation. SQLAlchemy column defaults only apply when the row is flushed to the database. Fix: set the values explicitly and call db.flush() when you need the id straight away.
2. Subtitles four times too bigThe style used FontSize = height/40, about 27. But libass measures subtitle styles against a 288-pixel-tall virtual screen, not the real 1080 px frame. Tests rendered at 320×180 and all passed; only looking at a real 1080p frame showed the problem. Lesson: always look at real output at real size.
3. Approving the final cut started an upload"Approve" continued to the next stage, and after QC the next stage is publish. The end-to-end test failed with "a job is already queued". Fixed as described in D13.
4. Couldn't redraw a scene while waiting at a later checkpointRegeneration only worked at the scene checkpoint, but you usually notice a bad image while watching the final cut. Now regenerating withdraws whatever checkpoint is pending (recorded in the approval history) and moves the project back to the right state.
5. The fallback "moral" was a half sentenceThe rule "last sentence under 12 words is the moral" picked "…said to his friend:". The rule now ignores sentences that end with a colon. Rule-based fallbacks need edge-case tests just like any other code.

Two techniques are worth copying. First, the engine tests inject fake stage handlers (run_job(job_id, settings, {Stage.SCRIPT: flaky})), so retry logic is tested without any AI. Second, the end-to-end test runs at 320×180 and 12 fps through environment overrides, so a full render takes seconds.

Going from offline to real AI

Each switch is configuration only. Check the result on the Settings screen, which runs the health checks.

  1. LLM: Ollama. Install Ollama, run ollama pull llama3.1:8b, then start with SPA_LLM_PROVIDER=ollama. Script writing, translation (Hindi becomes ready) and metadata switch to the model. If your model handles long text badly, lower max_source_chars.
  2. Images: ComfyUI. Export a workflow in API format into comfyui-workflows/ using the {{prompt}}, {{seed}}, {{width}}, {{height}} and {{reference_image}} tokens, set the checkpoint name, and use SPA_IMAGE_PROVIDER=comfyui. For consistent characters, build a scene_v2.json that feeds {{reference_image}} into an IP-Adapter node.
  3. Voices: Piper. pip install piper-tts, put hi_IN-pratham-medium.onnx and its .json in models/piper/. The voice registry already points to them.
  4. Animation: Wan 2.2 in ComfyUI. Put the four fp8 model files in ComfyUI's model folders (listed in comfyui-workflows/README.md), confirm ComfyUI's Wan 2.2 template renders, export it with tokens, then set SPA_VIDEO_PROVIDER=comfyui and create projects with style Hybrid animation. Draft at 832×480 and finish at 1280×720.
  5. YouTube. Create an OAuth desktop client in Google Cloud, save it as secrets/client_secret.json, run python scripts/youtube_auth.py, then SPA_PUBLISH_PROVIDER=youtube. Uploads stay private until you choose otherwise. Test against your project's real API quota before automating.

Recipe for your own AI content pipeline

The same structure works for podcast generation, course videos, product-demo videos, comic strips or localized audiobooks. In order:

  1. Write down the artifacts. List every intermediate thing that needs to exist (brief, outline, script, images, audio, timeline, video, metadata). Each one becomes a schema and a saved file.
  2. Draw the state machine. One stage per artifact. Note what each stage requires and produces, and where a human must look.
  3. Put every choice in config. Models, engines, sizes, languages and checkpoints, validated at startup and stored as a version hash.
  4. Define one interface per outside capability, and write an offline adapter next to each real one.
  5. Build the engine before the stages: a jobs table, one worker, transient versus permanent errors, backoff, checkpoints, and recovery after a crash. Test it with fake handlers.
  6. Fingerprint every generated item. Hash all its inputs, reuse when the hash matches and the file is intact, and change the seed to force a redo.
  7. Wrap every LLM call in three layers: schema-constrained output, Pydantic validation with a repair loop, then domain checks that feed errors back.
  8. Make legal and policy rules code: rights, attribution, disclosure and publish gates, checked again right before anything leaves the machine.
  9. Measure the output, not the intent. Write QC that probes the real files, and keep human approval for taste.
  10. Make every outside action idempotent: stable attempt ids, the record saved before the call, and a check for an earlier success before retrying.
  11. Build the UI last, as a view over backend state with no rules of its own.

Definition of done for an MVP like this

  • One story goes from source to private upload with every artifact saved
  • Killing the server mid-render and restarting it resumes the job without redoing finished work
  • A failed item can be retried alone
  • Every published video can be traced to its config version, prompts, seeds and rights decision
  • The publish endpoint refuses anything unapproved, even when called directly

Exercises

Each exercise touches one layer, so you learn the codebase a piece at a time. They go from easiest to hardest.

  1. Add Spanish. Add es to languages.targets and run with Ollama. Watch the Languages tab and the per-language render. (Config only.)
  2. Add a feed. Put a Creative Commons story feed in discovery.rss_feeds and discover from it. Note that it arrives as pending, not approved.
  3. Background music. Set video.music_path to a licensed track and listen to the ducking. Then add a QC check that the music is at least 12 dB below the voice.
  4. A Shorts template. Add a video.aspect setting and a 1080×1920 render variant that crops each scene to its centre. Add the matching QC rule.
  5. First-and-last-frame motion. Wan 2.2 also offers a first-last-frame template. Animate between two consecutive scene stills so cuts become smooth transitions. (Touches the video provider and the selection logic.)
  6. Character consistency. Build the IP-Adapter scene_v2.json workflow and compare scenes before and after.
  7. Episodes. For long sources, add a stage before script that splits the bible into episodes, each becoming its own project. (Touches the state machine, models and API.)
  8. Migrations. Add Alembic, generate the first migration from the models, and change startup to run alembic upgrade head instead of create_all.
  9. An LLM continuity reviewer. Add an optional QC check where the LLM reads the script and timeline and reports contradictions as warnings. Keep it advisory, never blocking.

Glossary

CheckpointA point where the pipeline stops for a person to approve or send back the latest stage's output.
FingerprintA hash of every input that affects an output. The same fingerprint means the output can be reused.
Transient errorA failure that may succeed on retry (timeout, server restarting). Permanent errors (bad config, missing model) are not retried automatically.
Story bibleThe structured summary of a story (plot, locations, characters, facts to preserve) that every later stage reads.
Reference sheetAn approved image of a character from several angles, used to keep their look consistent across scenes.
TimelineThe exact per-language schedule of scenes, lines and subtitle cues that the renderer follows.
Ken Burns effectA slow zoom or pan across a still image that makes illustrated narration feel alive.
IdempotentDoing it twice has the same effect as doing it once. Required for anything that talks to the outside world.
Soft subtitlesA subtitle track viewers can turn on or off, as opposed to subtitles burned into the picture. This pipeline produces both.
LUFSA loudness unit. Normalising to about −16 LUFS keeps your videos as loud as others on the platform without distortion.
